## [6.15.0] - 2026-10-23

> **Minor**: el plugin registra los hooks opcionales, y un miembro con solo el plugin, sin clon ni `NEB_HOME`, puede usarlos. Son `logbook-sync`, `usage-tracker`, `save-approved-plan`, `notify-on-stop`, `notify-on-permission`, `ops-capture` y `preprocess-prompt`.
>
> - **Activación voluntaria.** Cada hook corre solo si se activa con `NEB_HOOKS` (lista personal) o `NEB_PROJECT_HOOKS` (lista del proyecto), y corre la versión instalada del plugin.
> - **Saneo.** Desde 6.15.0, un `NEB_HOME` que un `/wakeup` anterior a 6.14.3 fijó al caché del plugin se ignora en el arranque, el CLI de pendings y logbook, los scripts de bootstrap y los skills, y el arranque avisa.
> - **Skills.** Los skills resuelven el plugin con `${CLAUDE_PLUGIN_ROOT}`, que Claude Code sustituye al cargarlos, en lugar de buscar la versión más alta del caché.
>
> Sin las variables, nada cambia donde Claude Code corre los hooks en Git Bash (Windows) o en `sh` (macOS y Linux). Sin Git Bash en Windows, ver Notas.

### Added

- **`hooks/hooks.json` — una entrada por hook opcional**, en forma shell, con un gate al frente:
  `case ",$NEB_HOOKS,$NEB_PROJECT_HOOKS," in *,<hook>,*) python "${CLAUDE_PLUGIN_ROOT}/hooks/neb-hook.py" <hook> || python3 … ;; esac`
  - **Apagado.** El gate cuesta solo el shell que Claude Code ya lanza (~50 ms en Windows), sin arrancar Python. Así deja de ser intrusivo registrarlos para todos, que era la primera razón de `hooks/README.md` para no hacerlo.
  - **Un comando para los dos sistemas.** Claude Code corre la forma shell en Git Bash en Windows y en `sh` en macOS y Linux, con el stdin íntegro, así que basta una sola línea. La segunda razón de `hooks/README.md` (`"shell": "powershell"` en Windows) venía de `cmd /c`, que ya no se usa.
  - **Timeouts.** `notify-*` tiene 10 s y `preprocess-prompt` 35 s.
- **`NEB_HOOKS` y `NEB_PROJECT_HOOKS`.** Son listas separadas por comas, sin espacios. El gate evalúa su unión, porque en el `env` de Claude Code el valor de proyecto sustituye al de usuario.
  - `NEB_HOOKS` es la personal: va en `~/.claude/settings.json` o en `settings.local.json`.
  - `NEB_PROJECT_HOOKS` es la del proyecto: va en su `.claude/settings.json` versionado.
- **`hooks/neb-hook.py` — dispatcher por nombre de hook.** Corre con el código de su propio árbol, aplica el guard de subsesión y siempre sale con 0.
  - `logbook-sync` y `usage-tracker` → sus módulos de `hooks/lib/`. El directorio de proyecto de `usage-tracker` sale de `transcript_path`, que es exacto: Claude Code también convierte `.`.
  - `notify-*` → el `.ps1` en Windows (`-ExecutionPolicy Bypass`) o el `.sh`.
  - `ops-capture` → se lanza **desacoplado**: Claude Code da 1.5 s a los hooks de `SessionEnd` al salir, y el `timeout` de un hook de plugin no lo amplía.
  - `preprocess-prompt` → con `PYTHONIOENCODING=utf-8` y su stdout, para que un prompt con tildes o `→` no se pierda por cp1252.
- **`hooks/lib/approved_plan.py` — `save-approved-plan` en Python, sin `jq`**, que no viene en Git Bash. Misma ruta y mismo encabezado. El slug es ASCII completo: `slugify.sh` usa `iconv //TRANSLIT`, que en Git Bash trunca en el primer carácter no ASCII («Instalación» → `instalaci`).
- **`hooks/lib/neb_root.py`.** `resolve_neb_root()` sigue el orden `NEB_HOME`, `CLAUDE_PLUGIN_ROOT` y el árbol propio, y descarta un `NEB_HOME` dentro de `…/plugins/cache/…`.
- **Avisos del arranque.** Avisa de un `NEB_HOME` en el caché, y ofrece borrarlo y pasar a las variables los hooks que lo usen. Avisa también de un valor desconocido o con espacios en `NEB_HOOKS` / `NEB_PROJECT_HOOKS`.
- **Tests.** `hooks/tests/test_neb_hook.py` (29), `test_neb_root.py` (14) y `test_hooks_json.py` (9). En Windows ubican Git Bash como Claude Code, no el `bash` de WSL. Este último cruza el gate de cada entrada con el dispatcher y prueba el gate en un shell real.

### Changed

- **Los templates de settings** (`hooks/settings.template.json`, `templates/claude-settings.json.template` y `templates/claude-user-settings.json.template`) ya no traen bloques que invoquen scripts de neb desde `$NEB_HOME`: traen las variables en `env`. El template de usuario conserva sus `PreCompact` (`auto` y `manual`).
- **`NEB_SRC`** en `skills/{wakeup,logbook,pendings-review}/SKILL.md` y `commands/{wakeup,logbook}.md`.
  - Toma el clon de `NEB_HOME` si no está en el caché; si no, `${CLAUDE_PLUGIN_ROOT}`, que Claude Code sustituye al cargar el skill. La forma anterior, `${CLAUDE_PLUGIN_ROOT:-…}`, no se sustituía, y por eso siempre caía al glob.
  - Se quita el glob `ls -d …/plugins/cache/*/neb/*/ | sort -V | tail -1`: ignoraba `CLAUDE_CONFIG_DIR`, y con dos marketplaces ganaba el último alfabético.
  - Si la raíz no se resuelve (un Claude Code sin la sustitución), avisa que hay que actualizarlo.
- **Docs.** `hooks/README.md` (§ «Bajo el plugin de Neb», § Activación, § Agregar un hook nuevo y la nota cross-OS de § Filosofía), `README.md` y `docs/user-guide.md` (requisito de Git Bash al instalar), `skills/wakeup/SKILL.md`, `tooling/{index,logbook,notify-on-stop,notify-on-permission,prompt-preprocessing}.md`, `workflow/{approved-plans,metrics,traceability}.md` y `templates/{change,approved-plan}.md.template`. Activación por variables, requisito de Git Bash en Windows, aviso de duplicados y el nombre del hook en vez del wrapper `.sh`.

### Fixed

- **`NEB_HOME` fijado al caché por un `/wakeup` anterior a 6.14.3** (la nota manual de 6.14.3). Lo ignoran:
  - El arranque (`bootstrap/neb-bootstrap-context.py`, precedencia D4).
  - El esquema del CLI de pendings y logbook (`_db_for_cli`) y el sync manual de `logbook.py`.
  - `bootstrap/setup-workspace.sh` (resolución del núcleo) y `bootstrap/init-profile-subproject.sh`.
  - El `NEB_SRC` de los skills.

  Antes, cualquiera de ellos corría la versión fijada o fallaba cuando Claude Code borraba esa carpeta, 14 días después del update.

### Notas

- **Para activar un hook con solo el plugin**, agrega su nombre al `env` de `~/.claude/settings.json`, por ejemplo `"NEB_HOOKS": "logbook-sync"`, y abre una sesión nueva. Si tu `settings.json` ya lo invoca desde `$NEB_HOME`, quita esa entrada: Claude Code no deduplica un hook de plugin contra una entrada de settings, y correría dos veces.
- **Windows requiere Git Bash.** Sin Git Bash, Claude Code cae a PowerShell, que no parsea el gate: las 9 entradas nuevas fallan en cada evento, estén activadas o no.
  - En PowerShell 5.1 tampoco parsea el `||` del `SessionStart`, así que Neb ya no arrancaba ahí; lo nuevo es el ruido de las otras entradas.
  - Con `pwsh` 7 y sin Git Bash, el `SessionStart` sí funcionaba, y estas entradas fallan: es una regresión, no verificada (no se tuvo `pwsh` 7 a mano).
  - Los snippets bash de los skills también requieren Git Bash.
- **El `.claude/settings.json` versionado de un proyecto** que invoque hooks desde `$NEB_HOME` falla en cada evento para un miembro solo-plugin. Reemplaza sus bloques por `"env": {"NEB_PROJECT_HOOKS": "…"}` en cuanto los miembros con clon tengan 6.15.0: con un plugin anterior, la variable no activa nada, y la entrada vieja ya fallaba para los miembros solo-plugin.
- **El maintainer con clon** puede conservar sus entradas de settings y no activar las variables. Los hooks activados con las variables corren el plugin cargado; para probarlos desde el clon, usa `claude --plugin-dir <clon>`.
- Validación:
  - **Suite.** 352 OK con y sin `NEB_HOME`, desde Git Bash y desde PowerShell; la línea base es 300.
  - **E2E con Claude Code real** (2.1.277, Windows) en un HOME simulado solo-plugin: el árbol en `…/plugins/cache/<mkt>/neb/6.15.0/` y pasado con `--plugin-dir`, sin `NEB_HOME` ni `NEB_WORKSPACE` y sin login. Las variables entraron por `--settings`, por el settings de usuario y por el del proyecto; `"NEB_HOOKS": ""` en `settings.local.json` apagó el de usuario.
    - `SessionStart`, `UserPromptSubmit` y `SessionEnd` del plugin corrieron en Git Bash, y `logbook-sync` escribió en el `neb.db` del HOME simulado.
    - `ops-capture` siguió vivo 6 s después de que terminó `claude`.
    - `preprocess-prompt` pasó intacto un contexto con tildes y `→`.
    - Sin las variables, el dispatcher no se invocó.
    - Los tres skills cargaron `NEB_SRC` con la ruta sustituida.
  - **`Stop`, `PreCompact`, `Notification` y `PostToolUse`**, simulados con el comando exacto de `hooks.json`, dejaron sus efectos: el costo en el draft, el work en `neb.db` y el plan aprobado.
  - **Una entrada vieja de settings** corre igual sin las variables; con `NEB_HOOKS` del mismo hook, corren las dos.
  - **macOS**, razonado: comandos POSIX (`sh -c`, con `python3` como fallback) y `start_new_session`.
